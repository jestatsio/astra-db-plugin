# Branding release proposal: 2.1.0

**Last assessed:** 2026-09-29. **Status:** branding merged; 2.1.0 authentication and release preparation in progress. Publication and live hosted verification remain separate gates.

Release 2.1.0 should establish **JEStats Astra DB Plugin** as a coherent JEStats product, with an explicit unofficial label and straightforward installation. The immediate distribution target is the self-managed preview pattern used by [JEStats Screaming Frog Plugin](https://github.com/jestatsio/screamingfrog-plugin). Official directory publication is a separate milestone.

## Scope and compatibility

Move the repository to `jestatsio/astra-db-plugin`; make JEStats the public publisher; use the [JEStats branding specification](branding.md) and original artwork across README, manifests, Desktop bundle, tool metadata, app UI, and hosted consent. The palette follows [jestats.io](https://jestats.io): charcoal `#111827`, cream `#FAF9F5`, and orange `#D9531E`. Put the unofficial notice beside the product name and installation instructions, not just in the license.

Keep plugin ID `astra-db`, marketplace ID `astra-db-marketplace`, MCP configuration key `astra-db`, command `astra-mcp`, and npm package `@erichare/astra-mcp`. Repository ownership and npm scope do not need to change together. Do not rename this independent marketplace to `jestats-plugins`, which the Screaming Frog project already uses, without designing a shared catalog migration.

The MCP Registry identity does need to change from `io.github.erichare/astra-mcp` to `io.github.jestatsio/astra-mcp` for publication using the transferred repository's GitHub OIDC identity. Update [server.json](../server/server.json) and `mcpName` in [package.json](../server/package.json) together in the newly published npm version. This is a new registry namespace; existing entries are not automatically renamed. The [registry implementation](https://github.com/modelcontextprotocol/registry/blob/main/internal/api/handlers/v0/auth/github_oidc.go) derives namespace permissions from the repository owner.

## Assessment: setup and credentials

The existing [resolver](../server/src/credentials/resolver.ts) resolves credentials per call from environment variables, project dotenv files, host settings, a global credentials file, and Astra CLI profiles. Token masking, credential hygiene hooks, hidden token input, scoped endpoint selection, and [doctor](../server/src/cli/doctor.ts) are useful foundations.

The 2.1 implementation adds **CLI-first connection setup**: reuse a detected source or named Astra CLI profile, save profile/config metadata without copying its token, and retain hidden token input as a fallback. Control-plane environments follow the selected credential source. This improves token handling without inventing unsupported upstream OAuth.

Merge owned fields while preserving existing credential and mode settings; test reinstall with `ASTRA_MCP_READ_ONLY=1` and custom environment values. |

The [official Astra CLI documentation](https://docs.datastax.com/en/astra-cli/manage-cli.html) and [setup implementation](https://github.com/datastax/astra-cli/blob/main/src/main/java/com/dtsx/astra/cli/operations/SetupOperation.java) still require an application token. [Data API documentation](https://docs.datastax.com/en/astra-db-serverless/api-reference/dataapiclient.html) also requires an endpoint and application token, including database-scoped tokens. [Astra SSO documentation](https://docs.datastax.com/en/astra-db-serverless/administration/configure-sso.html) describes SAML Portal login; this assessment did not establish a public third-party authorization-code or device flow for Data API credentials.

Upstream delegated OAuth is therefore a research dependency: obtain a documented issuer, client registration, scopes, and token exchange contract from DataStax before committing to browser-account login. The plugin's existing hosted OAuth is its own authorization server wrapping an Astra token; it does not mint upstream Astra credentials.

## Assessment: skills and distribution

- **Skills and hooks:** retain direct skill loading, shared dependency-free hooks, shortcut/persona metadata, and the generated Bob bundle. Validate actual installed workflows, not only file structure. Confirm provenance and redistribution rights for the bundled toolkit before asserting store eligibility; [NOTICE](../NOTICE) explicitly records missing upstream license terms.
- **Store package size:** the reviewed repository contains 1,915 tracked files, including 1,698 under `skills/`. Claude's [pre-submission checklist](https://claude.com/docs/plugins/pre-submission-checklist) places packages over 512 files on manual hold. Design a smaller store package with useful examples and indexed references; keep the full library available separately after rights confirmation.
- **Reproducible installation:** [agents.ts](../server/src/cli/agents.ts) and [smithery.yaml](../server/smithery.yaml) use the `@2` range. Official Claude review requires exact package pins and may still hold pinned `npx` installs for manual review. Store-specific artifacts should identify one source commit and published version.
- **Publication correctness:** 2.1 preparation makes registry errors fatal and requires exact metadata readback before GitHub assets are published. Release files include checksums. npm stage-only publishing requires maintainer approval before downstream jobs proceed.
- **Publisher migration:** update npm trusted publishing to `jestatsio/astra-db-plugin`, `release.yml`, environment `npm`; verify repository environments and [npm's OIDC requirements](https://docs.npmjs.com/trusted-publishers/). Retaining `@erichare/astra-mcp` does not remove this gate.

The current public baseline verified on 2026-09-29 is npm/GitHub release 2.0.0 and an active `io.github.erichare/astra-mcp` registry entry. A registry entry, npm package, or self-managed marketplace is not evidence of official Claude/OpenAI directory acceptance. The Screaming Frog reference records a development preview with host checks pending and directory submissions not performed.

## Release gates

1. **Branding/transfer review:** finish the concrete diff, verify the target repository, compatibility IDs, new registry identity, artwork, unofficial notice, and truthful privacy language.
2. **Publication preparation:** confirm bundled-content rights; configure publisher identities; fix release error reporting; decide whether high-priority setup/tool findings block the preview or are tracked for its next implementation release. Hosted publication must clear its authentication gates.
3. **Validation:** run repository integrity/version/example checks and server lint, typecheck, unit/tool/HTTP/CLI/eval tests, build, stdio smoke test, official AppBridge UI tests, plugin validation, and strict skill lint. Inspect built npm/MCPB/Bob contents; do not commit generated build output.
4. **Host verification:** exercise install, credential discovery, first useful query, read-only mode, reinstall, and uninstall using the actual distributed assets on macOS and Windows for Claude Code, Codex, and Bob; check Desktop/editor paths where claimed. Record OS, host version, artifact version/commit, and outcome. Use fake tokens in fixtures and a dedicated test account for live store review.
5. **Preview/release:** bump through the repository script, publish the exact npm version, read back its metadata/provenance, publish/read back the new MCP Registry version, publish GitHub assets/checksums, and check landing-page install paths.
6. **Official directories:** submit only artifacts whose platform-specific gates in [store-listing.md](store-listing.md) are complete; record submission, approval, and live listing URLs independently.
